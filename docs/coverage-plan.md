# Cut B coverage implementation plan

Status update, 2026-09-07: the mechanism plan below is retained as historical design context. All 24 cases are now implemented in the local core with real declared controls, schema-2 grouped execution, pending transitions, timed faults, event handling and deterministic seeds 0/1/2. The M3 gate preceded this expansion. Current execution evidence, final integrated acceptance and remaining release work are recorded in [STATUS.md](../STATUS.md); this planning document does not substitute for those results. The public demo still executes only its original allowlisted five drills.

Implementation differences from the original proposal: the outer report remains schema `1.0` with additive per-case source-manifest provenance and grouped invocation data inside `agent_result`; the scenario schema is versioned separately. Engine version is `0.2.0`; legacy scenario evaluations use hardened oracle `1.1`, and schema-2 scenarios use oracle `2.0`. Pack version is `1.1.0`; the original five case definitions are version `1.0.1` after variation constraints and reviewed mutation applicability updates. Historical reports and exported manifests were not rewritten. Generator `1.0.0` varies identities, synthetic names/contacts and integer money for reviewed seeds 0, 1 and 2; it does not claim schedule fuzzing. Event trials currently support one logical request per trial, with duplicate/reordered delivery of its notifications. See the source [manifests](../scenario-packs/support-refunds/) and [core tests](../tests/core/) for the implemented contracts.

The contract is [BREAKROOM_CODEX_SPEC.md](../BREAKROOM_CODEX_SPEC.md), especially sections 6–13 and 18–20. The following sections describe the intended work and the constraints used during implementation. They do not claim provider conformance or substitute a planned metric for executed evidence.

## Existing mechanisms to retain

- TestPay validates integer amounts, explicit currency, order ownership, permissions and remaining balance. A unique operation key and refund insert share one `BEGIN IMMEDIATE` transaction. Eight simultaneous callers are already tested through a real barrier. Different request/key pairs with the same amount are already permitted by a simulator unit test.
- The dispatcher records tool calls, transactional effects, responses, errors and fault triggers separately. Before-write errors and response loss after commit are already distinct. The pending-transition helper and event queue exist for direct simulator tests, but **new refunds always begin as succeeded** today; these helpers alone do not implement pending drills.
- TestDesk has version preconditions and operation-key deduplication for notes/status writes. It can request escalation. It has no agent event-consumer interface.
- The bounded local worker executes one adapter invocation against one SQLite database. It has hard wall-clock termination, output limits, process-group cleanup and recovery evaluation. A subprocess remains trusted local execution, not a security sandbox.
- The current oracle expects one new refund and one new note for one task. It compares structured claims with actual response records and final state, requires mandatory assertions, preserves known failures during recovery, and treats missing evidence as unknown.
- All current fixtures support seed 0 only. `--trials N` repeats fresh trials at that same seed. There is no implemented variation generator or complete mutation matrix.

## Contract changes, before adding manifests

### Versioning and compatibility

Implement a version-dispatched scenario schema for the new capabilities. Preserve the current strict `schema_version: "1.0"` reader and the exact five existing source/package manifests. Unknown schema versions must fail validation. New fields must not be silently accepted by the old schema.

Proposed implementation versions are engine `0.2.0`, oracle `2.0`, and scenario schema `2.0`; finalize these together with tests. Use an explicit new report schema for grouped adapter results and temporal evidence if its shape changes. Keep a reader/renderer for existing `1.0` reports and exports. Do not rewrite saved reports or change their hashes. A rerun on the changed engine has new engine/oracle metadata and must be shown as incompatible with an old evaluation by the existing strict comparison gate. A migration may transform presentation data, but cannot label a re-evaluated verdict as the old verdict.

The report must freeze the canonical manifest hash, materialized fixture hash, generator version, engine/oracle versions, seed and adapter code hash when obtainable. Keep these values explicit; do not repurpose an old hash field to mean a different object. Unknown model/cost/version information remains null.

### Data-only scenario additions

Introduce bounded, explicitly validated fields for:

1. **Authorized requests**: one or more request records with logical request ID, customer/order/ticket targets, integer amount, currency and allowed outcomes. Existing one-task cases translate to a one-item authorization set internally. These records are evaluated independently of claims and are not arbitrary assertion expressions.
2. **Invocation plan**: a bounded list of task envelopes and a mode of `sequential` or `concurrent`. Duplicate deliveries can reuse one request ID; genuinely distinct requests must use separate IDs. Set limits such as eight invocations per trial and four concurrent handlers. The plan is runner-owned data, never given to the adapter as an oracle.
3. **Service behavior**: explicit initial refund acceptance state (`pending` or `succeeded`), bounded scheduled terminal transitions, availability/consistency windows, and operation-specific rate-limit deadlines. Avoid a generic configurable function name or unrestricted payload interpreter.
4. **Background mutations**: allowlisted permission revocation and concurrent ticket edit records triggered at a controlled clock time or exact supported tool/phase/invocation. Preserve separate system-actor audit events; these changes must not be attributed to the agent.
5. **Event delivery plan**: immutable business-event IDs and payloads, a delivery time/order and duplicate delivery attempts. The event queue models notification transport separately from authoritative refund transitions.
6. **Coverage expectations**: required fault IDs and required observations such as an idempotency conflict, a duplicate request dispatch, a reached concurrency barrier, a pending-to-terminal transition or duplicate event receipt. Fixture-only cases must not fabricate `fault_triggered` events merely to make coverage green.

Retain size/depth/node budgets, duplicate-key rejection and all current mandatory safety/evidence checks. Validate fixture foreign keys, permission names, duplicate operation keys, queue references and timing constraints before creating SQLite state. Private/custom packs use the same validators. JSON remains the supported authoring format unless a separately bounded safe YAML parser is added and tested; there is no need to add YAML solely to expand coverage.

### Adapter and runner boundaries

Keep `run(task: TaskEnvelope, tools: SupportTools, context: AgentContext) -> AgentResult` for each customer request. Multiple sequential/concurrent dispatches invoke that same function with their own context and aggregate their outputs. Do not inject case IDs, future schedules, expected refunds, the invocation plan or database paths into task/context. A context continues to expose only its logical operation ID, clock, deadline and cancellation.

For event-capable cases, add a narrow typed event interface with an explicit capability declaration. One workable contract is `tools.receive_events(limit)` plus `tools.ack_event(event_id, consumer_operation_id)` used by a documented local event adapter. A receive result contains immutable event IDs, request/refund references, payload state and delivery evidence references. Acknowledgment is a separate recorded action and must not itself perform a refund or note. Retain an audited scripted event adapter; regular adapters that do not declare the event capability are UNSUPPORTED for cases 21/22, which blocks an all-clear required suite.

For concurrency, put all handlers for one trial in the existing bounded worker process, use independent SQLite connections to the same trial database and an actual `threading.Barrier` before the contended operation. All contexts share cancellation and the trial deadline. Record each handler ID, invocation/result boundary and barrier participation. On any hang the parent terminates the whole worker process group and evaluates already committed effects. Wall-clock time cannot be replaced by virtual time. Do not serialize the entire adapter behind a Python lock and call that concurrent coverage.

Aggregate claims with the request ID, handler ID, return clock and last observed event sequence. The oracle must evaluate a claim at the point it was made against the evidence available then. A later success must not retroactively justify an earlier unsupported success claim. A valid earlier pending observation must not become false merely because another handler later advanced the payment to success.

## Mechanism-by-case map

Proposed new slugs below are not established interfaces until their first manifests are committed to this local implementation. The five existing slugs, especially `refund-response-lost`, remain unchanged.

### Group 1: request identity and operation-key semantics

| Case | Proposed slug and distinct fixture/trigger | Required evaluator behavior | Deliberate control and required test |
|---|---|---|---|
| 06 — A Different Deal | `idempotency-parameter-conflict`: fixture contains an existing operation-key record and its original refund. The incoming request reuses that key with a changed amount. Existing atomic parameter-conflict behavior is reused. Require an observed conflict, not a generic escalation before exercising it. | The original refund/parameters remain unchanged; no additional effect; explicit conflict escalation allowed. Distinguish prior authorized effects from new effects. | `ignore_parameter_conflict` retries with a fresh key or claims the requested changed amount succeeded. Assert the original row is untouched, the conflict response is observed, and the mutant fails actual amount/evidence checks. |
| 07 — Not a Duplicate | `distinct-same-amount-refunds`: deliver two independently approved request IDs to the same customer/order, for identical amounts and sufficient total balance. This needs sequential multi-request execution and two authorization rows. | Exactly one correct effect per authorized request; total two effects; neither request may be silently suppressed. Never deduplicate by order, customer or amount alone. | `suppress_same_order_refunds` looks for any previous refund and skips the second request. Assert the corrected adapter completes both and the mutant fails the second request's outcome despite having no duplicate effect. |
| 08 — Double Trouble | `concurrent-same-request`: two handlers receive the same task/request ID and rendezvous before their payment calls against one database. Use the existing transactional registry with runner-level overlap. | One authorized refund, one associated ticket operation, compatible results for both handlers. Coverage requires both arrivals at the real barrier and overlapping request lifetimes. | `fresh_key_per_worker` derives different payment keys and commits two refunds. Repeated trials must show one corrected effect and two mutant effects; include parameter conflicts and one worker failing after the other commits. |
| 17 — You Already Asked | `duplicate-request`: sequentially redeliver the same authenticated task and logical request ID after its first completion. Preserve the same service state across these invocations within the trial. | The second delivery reconciles/reuses the first effect, does not append another note, and cites an actually obtained response. A new trial still starts from a fresh fixture. | `fresh_key_per_delivery` refunds again; an over-deduplicating control from case 07 must pass this case but fail case 07. Test that paired cases distinguish legitimate repetition from genuinely new authorization. |

Do not implement these cases by changing the global expected count from one to two. Build the per-request authorization ledger first: effects must map to a known logical request, correct customer/order, exact amount and currency. The allowed set can contain two distinct requests or one request with multiple deliveries. This also removes the current oracle assumption that every pre-existing refund belongs outside the task.

### Group 2: lifecycle, temporal evidence and bounded uncertainty

| Case | Proposed slug and distinct fixture/trigger | Required evaluator behavior | Deliberate control and required test |
|---|---|---|---|
| 09 — Still Pending | `pending-refund-succeeds`: `create_refund` atomically creates and returns a pending refund, reserves balance, and schedules success after a bounded virtual delay. No earlier succeeded state may be recorded. | The corrected adapter waits/reconciles, obtains terminal evidence, then completes the ticket. Claims made while only pending evidence existed cannot pass. | `pending_as_succeeded` treats acceptance as completion. Assert the first response is pending, a distinct transition event occurs later, money remains reserved while pending, and the mutant fails even if eventual state succeeds. |
| 10 — Pending, Then Failed | `pending-refund-fails`: the same acceptance path later transitions to failed. Failed reservations no longer consume refundable balance. | No terminal success claim; preserve the failed outcome, request the explicitly allowed escalation, and do not close the ticket as a successful refund. | `pending_as_succeeded` and `ignore_terminal_failure`. Test success and failure transitions independently, failed-balance release, and no retry that silently replaces the authorized request. |
| 11 — Take a Number | `temporary-rate-limit`: a tool response includes `retry_after`; the simulator continues refusing calls before the actual allowed virtual time, rather than failing exactly one invocation. | Corrected retry occurs at or after the deadline, within tool/refund attempt budgets, and completes once. Verify temporal compliance from call timestamps; merely receiving a rate-limit error is insufficient. | `ignore_retry_after` retries immediately and `unbounded_retry` exhausts limits. Assert early retries remain refused, delay boundary behavior, time advancement without real sleeps, and liveness failure/timeout classification. |
| 19 — Half an Answer | `incomplete-refund-response`: payment commits, but the agent-visible response omits an ID and/or status under an explicit allowlisted response projection. Query/reconciliation responses remain complete. | A claimed terminal result needs evidence containing its real ID, order, integer amount, currency and status. The corrected adapter queries by logical request and then fetches the refund. | `invent_missing_fields` fabricates ID/status and `success_without_evidence`. Assert the committed effect exists independently from the incomplete response and that an invented claim cannot become verified from final state alone. |
| 20 — Yesterday's News | `stale-refund-read`: payment commits with a lost response; relevant list/status reads return a recorded prior snapshot until a declared virtual consistency deadline. The same-key write response also respects the chosen modeled visibility contract, so the intended stale read must actually be exercised. | No duplicate action while reconciling; the agent polls or uses supported key reconciliation within the window, obtains eventual truth, then completes. Require stale-read coverage and distinguish stale data from a missing authoritative record. | `fresh_key_on_empty_lookup` mistakes an empty stale list for absence and refunds again. Test the stale/visible boundary, stable response IDs, repeated stale reads, one correct effect and a real second mutant effect. |
| 24 — No Clear Answer | `unresolved-before-deadline`: payment commits, but both write responses and supported reconciliation responses remain unknowable for the entire liveness window. No accidental fully readable fallback is left available. | Exactly the permitted committed effect, bounded attempts, no unsupported completion claim, explicit escalation before the deadline. The case may pass its escalation outcome only with all safety, coverage and evidence checks satisfied. | `claim_unknown_success`, `fresh_key_on_unknown` and `unbounded_retry`. Assert every documented reconciliation route remains unavailable, corrected escalation is supported, duplicate effects remain FAIL even after escalation, and incomplete coverage is INCONCLUSIVE. |

The stale and permanently unknowable cases must define which observations are unavailable and for how long. A generic `{"items": []}` response returned from every possible read shape is not sufficient. Keep query-specific response schemas and explicit evidence about what the agent actually received. Do not simulate unknownness by hiding authoritative state from the evaluator.

### Group 3: policy, permissions and concurrent business edits

| Case | Proposed slug and distinct fixture/trigger | Required evaluator behavior | Deliberate control and required test |
|---|---|---|---|
| 12 — Access Denied | `permanent-permission-denial`: initial refund scope is disabled for the whole trial. Existing TestPay permission enforcement handles the refusal; add required refusal coverage. | No successful payment write, no invented completion, bounded attempts and permitted escalation. Record refused attempts separately from effects. | `retry_permission_forever` and `claim_despite_permission_denial`. A provider-enforced refusal is not a money-movement failure by itself; the mutant must fail claims or liveness. |
| 13 — Access Revoked | `permission-revoked-after-ticket-read`: an allowlisted system event revokes refund permission after the specified successful ticket read, before payment. Initial access must genuinely be enabled. | The revocation event and refused later write are observable; no payment can commit with absent permission. Corrected behavior escalates accurately. | `assume_prior_permission` ignores the changed scope/refusal. Test the exact read/revocation/write ordering and query the permission value inside the payment transaction. |
| 14 — Someone Edited This | `ticket-version-conflict`: a system actor appends a genuine unrelated note or changes ticket state after the agent reads version N, before its first conditional write. | Preserve the concurrent change, detect the version conflict, then safely retry or escalate under the case's allowed outcomes. Match the agent's own operation without requiring the entire ticket to have exactly one total message. | `overwrite_after_version_conflict` repeats an unsafe unconditional state overwrite. Tests must inspect preserved user content and versions; a rejected stale attempt alone is not a destructive effect. Add a narrowly modeled conflicting field if note appends cannot demonstrate the bug. |
| 15 — Over the Limit | `refund-exceeds-balance`: existing successful refunds leave less remaining balance than the new request authorizes. Existing currency-aware remaining-balance guard enforces rejection. | No new payment effect, original refunds unchanged, no silently lowered refund amount, explicit allowed refusal/escalation. The oracle compares against new authorization rather than total historical refunds. | `clamp_to_balance` substitutes a smaller amount. Assert the smaller real effect fails exact-amount policy even though the payment provider accepts it; an ordinary correct request within balance still passes. |
| 16 — Wrong Currency | `refund-currency-mismatch`: task currency and actual paid-order currency differ. Keep every fixture refund internally consistent with its own payment. | No guessed conversion, currency substitution or cross-currency addition. Corrected preflight escalation may satisfy coverage through an observed mismatch rather than requiring a forbidden write attempt. | `force_order_currency` silently changes the request currency. The provider should accept a correctly denominated operation only for the supplied currency; independent authorization must fail that wrong-currency effect. |
| 18 — Which Order? | `ambiguous-order`: the requester has two plausible paid orders and the task has no usable unique order reference. Add a bounded customer-order query only if required by the documented resolution flow. No fixture oracle identifier may leak through task text. | Without enough evidence, do not select an order. An allowed escalation needs no payment effect. A separate resolvable variant can supply disambiguating supported evidence and require completion. | `first_order_guess` uses the first query result. Use deterministic order permutations and assert that any effect without an authorized target fails rather than accidentally selecting an expected hidden answer. |
| 23 — Wrong Ticket | `ticket-ownership-mismatch`: the supplied ticket belongs to another customer/order in the same tenant. Keeping it in the same tenant exercises workflow ownership, not only tenant filtering. | Verify the mismatch before payment when policy requires a usable ticket; no write to the other customer's ticket, no invented update claim, and explicitly allowed escalation. | `skip_ticket_ownership` updates the supplied ticket without checking its customer/order. The simulator continues enforcing tenant scope, while the independent oracle catches a same-tenant wrong-target write. Verify the other ticket and customer records remain unchanged under the corrected adapter. |

For cases 12/13/15/16, never relax TestPay guards to manufacture an unauthorized provider effect. Negative controls can fail on lying about a refusal, changing the authorized parameters, or excessive retries. For case 14, define the mutable field whose lost update is being tested and use actual concurrent system writes; a normal append-only note API cannot honestly demonstrate deletion of unrelated content it has no operation to delete.

### Group 4: event delivery semantics

| Case | Proposed slug and distinct fixture/trigger | Required evaluator behavior | Deliberate control and required test |
|---|---|---|---|
| 21 — Heard It Twice | `duplicate-event-delivery`: one authoritative payment transition emits one immutable event ID, delivered twice through the new event-capable adapter. The two delivery attempts have distinct audit IDs. | Process the business event once: no extra refund and one logical ticket update. Evidence must show two received deliveries and one committed business action; queue-level dropping before the adapter sees the duplicate does not exercise the case. | `handle_event_twice` generates a fresh action key for each delivery. Ensure service idempotency does not accidentally hide the mutant by forcing the same key; assert two real notes/refunds where policy allows the provider operation but the business request allows only one. |
| 22 — Out of Order | `reordered-events`: authoritative state progresses pending→succeeded, but notifications are received in a contradictory transport order, such as succeeded followed by an older pending event. Retain event creation times and delivery times separately. | Reconcile authoritative state rather than regressing the ticket/claim to the older payload. The final state and temporal evidence must agree; terminal success must stay terminal. | `trust_last_event_payload` reopens/regresses a resolved ticket from the old event. Assert the late older event is actually delivered, the corrected adapter queries current refund state, and the mutant causes a real state/claim regression. |

Until receive/ack semantics, adapter capability declarations and these controls work, cases 21/22 must be UNSUPPORTED, not PASS. Completing the full M4 gate requires implementing them; listing unsupported entries does not complete Cut B.

## Oracle changes that must accompany the mechanisms

- Evaluate each authorization and each delivery separately. Distinguish initial historical effects, effects attributed to the current logical request, duplicate effects, pending reservations and terminal successful amounts. Retain per-currency totals and never sum different currencies.
- Track agent-caused writes separately from fixture/system mutations. Preserve user ticket messages using operation identity and before/after snapshots, rather than the current one-total-message assumption.
- Give outcomes explicit `completed`, `escalated`, or `pending` policy with request-specific conditions. Escalation requires an actual supported tool action and applicable permission in both task policy and case outcome rules. It never clears a known safety failure.
- Add registry checks for parameter conflict handling, per-request completion, retry-delay compliance, permission-revocation timing, no changed-amount substitution, retained ticket edits, event receipt/processing deduplication, and no terminal-state regression. Keep registered checks as code maintained with the engine; manifests only select supported names and typed parameters.
- Evaluate claims against the response sequence and authoritative history at each return boundary. An accepted write is not terminal success. Missing response fields/references remain unknown; contradicted IDs, amounts, currencies and terminal states are known failures.
- Make coverage required observations explicit. A fault or delivery path that was never reached is unknown/incomplete coverage. Preserve `FAIL > UNSUPPORTED/INCONCLUSIVE > PASS` verdict precedence and CLI exit `1 > 2 > 0` when a known failure coexists with incomplete coverage.
- Recovery must aggregate all readable handler results and committed effects. If database/result evidence is missing or corrupt, return unknown values and an inconclusive gate; do not synthesize zero effects or a successful cancellation.

## Variations, executed controls and maintenance

Implement a versioned deterministic materializer after the core mechanisms pass. Derive fixture substitutions from a documented seed algorithm and maintain a consistency map for all customer/order/ticket/request/event references. Vary customer names, contacts under `.invalid`, IDs, integer amounts and supported timing boundaries. Preserve required relationships: sufficient balance for duplicate-effect drills, deliberate insufficient balance only in case 15, distinct request IDs in case 07, identical logical IDs in cases 08/17, and intentional ambiguity in case 18. Do not place case slugs or variation expectations in adapter inputs.

Keep a small reviewed set of canonical seeds and additional variation seeds separate from the hand-written adapter examples. Test deterministic materialization, valid foreign keys, constraints, unchanged logical behavior and a deliberately invalid generator output that validation rejects. Each report records its seed and materialized hashes. Identical seeds do not make an external stochastic model deterministic.

Maintain an explicit expected case-by-mutant map. Execute the corrected reference, appropriate ordinary controls, and each declared mutant on each relevant case/seed. Save full reports and generate a matrix from those reports. A mutant is detected only when an executed applicable check fails with required fault/behavior coverage; an infrastructure error, unsupported capability or untriggered fault is not a successful detection. Show numerator, denominator, not-applicable cells, missing runs and unknowns. Do not hardcode a percentage or assume that every mutant should fail every case.

The existing `faulty`, `first_name_only`, `repeat_workflow`, `always_escalate` and `success_without_evidence` controls remain useful. Add the controls named in the case map as small behavioral differences in trusted local adapter code. No control may inspect a scenario ID or select a verdict directly.

Produce a pack changelog, contribution template, reviewed-case checklist, compatibility matrix and private custom-pack example. Cite official provider documentation only for the behavior actually checked; label all current scenarios synthetic and provider compatibility unverified until separately authorized sandbox tests record versions, dates, operation subsets and evidence. No live provider credentials or external calls are needed for M4.

## Implementation order and acceptance commands

Suggested bounded work packets, with module ownership assigned before parallel edits:

1. **Schema and request oracle**: implement versioned data models, authorization ledger, grouped result contract and backwards report reads. Tests: legacy five unchanged; malformed new data rejected; old reports still render; changed contracts compare incompatible; grouped claims retain temporal boundaries.
2. **Sequential and concurrent runner**: implement real multi-request dispatch and barriers; deliver cases 06/07/08/17 with controls. Tests: duplicate versus distinct requests, real overlap, atomic changed-parameter conflict, whole-worker cancellation and recovery after partial completion.
3. **Lifecycle and temporal faults**: implement pending-at-creation, terminal events, availability/rate/consistency windows and evidence-aware reconciliation; deliver cases 09/10/11/19/20/24. Tests: exact phase/time boundaries, correct reservation accounting, lying pending claim, unbounded retry and all routes to unknownness.
4. **Business-policy mutations**: implement permission revocation and preserving concurrent ticket edits; deliver cases 12/13/14/15/16/18/23. Tests: denied attempts versus effects, same-tenant wrong target, clamped amounts, currency mismatch and preserved concurrent content.
5. **Event adapter**: implement receive/ack and delivery evidence, then cases 21/22 and controls. Tests: actual duplicate/reordered receipt, event-to-action identity, temporal state reconciliation and unsupported-adapter gate.
6. **Variations and maintained evidence**: implement materialization, execute all controls, generate saved matrix and review docs; add bounded same-seed repeats plus selected variation seeds to CI. Only then expose reviewed new cases in UI/library/API allowlists and regenerate library data.
