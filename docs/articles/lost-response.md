# The refund succeeded. The response disappeared.

This walkthrough reproduces a synthetic failure in [Fire Drill — The Missing Response](../../scenario-packs/support-refunds/refund-response-lost.json). TestPay and TestDesk are original fake services. The records, customers, money, and failures are simulated; the agents are scripted controls. This is not a production incident or a benchmark of a commercial model.

A timeout tells the caller that it lacks a response. It does not, by itself, establish whether the write committed. Breakroom makes that ambiguity visible by recording tool calls separately from authoritative business effects.

The fixture has a paid order of 500000 INR minor units and authorizes a partial refund of 100000 INR minor units. In the lost-response drill, TestPay commits the refund and its operation-key registry entry inside a SQLite transaction. The fault then raises a transport-timeout error before returning the response. The first committed refund remains in the database.

The [faulty reference](../../packages/breakroom-core/src/breakroom/agents.py) retries with a fresh key. Because sufficient refundable balance remains, TestPay accepts a genuinely separate second refund. The agent receives that response, updates the ticket, and returns normally. Its process has completed, but it has refunded 200000 INR minor units for a request authorizing 100000.

## Reproduce it

From the repository root, install the local core and execute both controls:

```sh
python -m pip install -e ./packages/breakroom-core
breakroom demo --output artifacts/missing-response
```

The observed faulty result is `completed / FAIL`: two refund records totaling 200000 INR minor units. The corrected result is `completed / PASS`: one record totaling 100000 INR minor units. Inspect `artifacts/missing-response/report.html` or the JSON bundle to see the underlying events and checks. The report is generated by real trials; these numbers are not selected by the agent's name.

For separate release checks:

```sh
breakroom run --agent examples.agents.faulty:run --pack support-refunds --case refund-response-lost --out artifacts/missing-response-baseline
breakroom run --agent examples.agents.corrected:run --pack support-refunds --case refund-response-lost --out artifacts/missing-response-candidate
breakroom compare artifacts/missing-response-baseline artifacts/missing-response-candidate
```

The first command intentionally exits 1. Run the next command separately if your shell stops on failures. In the failed report, inspect `no_duplicate_effects`, `amount_authorization`, and `exact_amount`, then locate the two `refund_committed` events. The tool-error event is after the first commit. A refused operation would not create a committed refund record.

## What changes in the corrected agent

The corrected reference uses `context.logical_operation_id` as a stable operation key. Repeating that key with the same parameters returns the prior refund within this modeled registry lifetime. The registry is checked and written atomically in SQLite; real overlapping operations are covered by a core concurrency test. Reusing the key with changed parameters produces an explicit conflict.

The correction does not deduplicate every refund on the order. Two distinct authorized operations may legitimately have matching amounts. The key identifies the operation, not a customer name or amount. This simulator models a limited generic behavior; no payment provider conformance is claimed.

## Keep the failure as a regression

```sh
breakroom export-case artifacts/missing-response-baseline --case refund-response-lost --out regressions/missing-response
python regressions/missing-response/test_regression.py --agent examples.agents.corrected:run
python regressions/missing-response/test_regression.py --agent examples.agents.faulty:run
```

The corrected command passes and the faulty command fails. The export freezes the case JSON and contract versions and runs a new isolated trial against the selected local adapter. It does not reclassify a screenshot or reuse a saved passing label. The resulting assertion checks the actual business outcome, while the report retains execution, claims, coverage, and safety checks separately.

The useful claim is narrow: this drill detects the implemented fresh-key retry bug under its modeled conditions. It does not establish universal safety, provider certification, or deterministic behavior for a network-backed model.
